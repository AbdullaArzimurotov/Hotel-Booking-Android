# API — этап 1, версия 0.1.0

## Реализовано

`GET /health` — liveness без обращения к базе. HTTP 200:

```json
{"status":"ok","service":"hotel-coursework","version":"0.1.0"}
```

`GET /api/v1/health` — readiness; каждый запрос делает `SELECT 1` через Exposed/JDBC.
При доступной базе HTTP 200:

```json
{"status":"ok","database":"connected","service":"hotel-coursework","version":"0.1.0","stage":1}
```

Если база перестала отвечать, HTTP 503, `status=degraded`, `database=unavailable`.
Пароли, JDBC URL и внутренние исключения клиенту не передаются.

Перед началом прослушивания порта сервер проверяет параметры окружения и выполняет Flyway.
Без правильной базы/пароля первоначальный запуск завершается ошибкой, а не создает
фиктивный успешный ответ. Секреты передаются скриптом запуска через окружение.

## Запланировано, еще не реализовано

`/api/v1/auth`, `/locations`, `/hotels`, `/rooms`, `/bookings`, `/payments/demo`,
`/receipts`, `/profile`, `/places` и `/admin`. На этом этапе они возвращают 404.

Будущие `/places` будут общим справочником города со связью с гостиницами.
В услугах заказа будут храниться реквизиты аэропортного трансфера.
Это требуется отразить в следующих миграциях и обновленной ER-модели.

Плановые статусы заказа: PENDING_PAYMENT, CONFIRMED, CANCELLED, COMPLETED.
Плановые методы: ONLINE_DEMO и PAY_AT_HOTEL. Программной реализации этих операций пока нет.
